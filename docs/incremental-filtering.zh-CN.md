# 增量筛选与读取流水线

日期：2026-11-22。分支：`codex/progressive-csv-loading`。

## 行为

筛选不需要等整个文件读完。用户提交条件后，先扫描已经提交的源记录，按源顺序尽早发布匹配行；后台每批新增记录只筛选一次，并将新命中追加到结果。条件修改、撤销、重做会取消旧版本任务，用新条件重新扫描当时已加载的前缀。旧响应不能混入当前结果。

加载中的表格始终区分三种数量：

- `rowsRead`：已提交到基础表的源记录数。
- `query.scannedRows`：当前条件已经扫描的源记录数。
- `query.generatedRows`：已发布的匹配记录数。

`query.exactTotal` 在完整读取及当前条件扫描完成前保持为空。前缀零命中显示“已加载部分暂未找到匹配记录”，后台继续读取，不能据此判断整个文件没有命中。

候选菜单可查询当时已加载的部分，应用其他列条件并排除本列条件，最多保留 200 个不同值、8MiB 完整字段。候选标记 `partial=true`，不提供全文件精确数量；可以手动刷新已加载候选，完整读取后自动重新查询完整候选集合。全选搜索命中保存为条件规则，后续读取的新值仍可命中，不受当前候选样本限制。

完整的全局排序仍须读取后面的数据。用户提前设置排序时，加载阶段先显示满足筛选的源顺序结果，并提示排序待完成；完整数据就绪后再生成全局有序索引。编辑、删除、标色和另存为继续在完整数据就绪后开放。

以上增量扫描用于首次导入和重新构建缓存。复用已有基础缓存时仍先校验整个源文件的内容指纹，校验前保留有限预览和已设置的条件；校验通过后开放缓存查询，避免仅凭大小和修改时间展示过期内容。

## 架构

```mermaid
flowchart LR
    CSV[CSV 源文件] --> Parser[严格解析 / 编码校验 / 指纹]
    Parser --> Queue[有界 Arrow 批队列]
    Queue --> Writer[独立连接分批提交]
    Writer --> Base[一份 DuckDB 基础表]
    Base --> Scan[当前条件按新增 rid 范围扫描]
    Scan --> Index[仅保存匹配源行号]
    Index --> Page[按结果位置取行号]
    Base --> Page
    Page --> UI[只返回当前页的可见列]
```

### 读取

一个生产线程独占 CSV 状态机，严格处理编码、引号内换行、列宽与预算，并生成 Arrow 批。另一个消费线程执行数据库 Appender 和事务提交，两步可以重叠。队列容量为 1，写入慢时解析自动背压。首批仍优先提交预览；后续批次按约 8MiB（含字段、Arrow offsets 和行号）或 32,768 行提交。

跨文件共享 128MiB 的 Arrow 缓冲准入池，在分配批构建器前预留包含最大记录及缓冲扩容的估算额度，批被消费或丢弃后归还。它不是整个进程的内存硬上限：解析器、DuckDB、WebView2 和自定义的超大记录预算仍有额外内存成本。

写连接与加载期的小查询连接分开，读取已提交前缀不会和写入共用一个连接互斥锁。增量筛选每次最多处理 32,768 条源记录，页读取及部分候选与这些小查询共用受保护的读连接。完整查询、排序、导出和导入提交仍使用应用级重任务调度；加载中的有界前缀查询属于轻任务。

### 查询

筛选和排序结果只写连续的 64 位源行号文件，每个匹配行占 8 字节。筛选、排序完成后，不额外保存一份所有可见列的完整结果。表格要显示或复制时，才取所需位置的行号，并在基础表中读取对应行列，保留索引顺序；展开新列也不重新执行筛选或排序。

加载期间的增量筛选沿用现有参数化 SQL 编译器，所以文本、精确数值、无时区日期、多列 AND、搜索选择规则和长字段引用的语义相同。已扫描前缀不会在每批提交后重扫。无排序时，EOF 前后的同一查询和同一行号索引继续使用；尾部扫描完成后才发布精确数量。

未筛选、未排序的默认视图直接按源行号范围分页，无需全表结果索引。候选集合继续使用独立的 Arrow 值存储，因为它需要保存去重值。

### 生命周期

取消或解析错误停止解析、使旧查询失效、清理未发布缓存。消费端失败时先丢弃接收队列，再等待生产线程结束，避免生产线程被满队列永久阻塞。缓存最终移动前等待当前小查询结束；移动期间的分页请求以过期状态重试，增量扫描随后继续使用正式基础缓存。

生产线程即使提前读到 EOF，也通过独立文件句柄将源文件的稳定只读租约保留到缓存发布结束。同一文件版本的并发导入使用单独的发布锁，串行检查目标是否已存在，避免两个发布者同时重命名到同一个缓存目录；读取者的共享缓存租约不会阻塞这个发布锁。

## 验证

`scripts/test.ps1` 包括版本一致性、前端测试、生产构建和 Rust 工作区测试。增量回归覆盖读取期间筛选/复制/撤销/重做、前缀零命中、后续新增命中、多列条件与搜索选择、部分候选、全局排序切换，以及取消和错误尾部不发布缓存。现有编辑、长值、编码、排序、导出与缓存验证继续保留。

原生入口：

```powershell
. .\scripts\environment.ps1
cargo test --workspace --features csvscope/custom-protocol --locked
cargo build --release --workspace --features csvscope/custom-protocol --locked
.\target\release\csvbench.exe open .bench\regular-1g.csv <新缓存目录>
.\target\release\csvbench.exe stream-filter .bench\regular-1g.csv <另一个新缓存目录>
```

`stream-filter` 验证在文件仍准备时读取并核对首批筛选结果、后续追加命中、EOF 保持查询 ID，以及最终精确数量。真实桌面入口 `scripts/desktop-smoke.ps1 -Release -Files ...` 还会操作 Canvas 列菜单，在加载期查询部分候选并确认筛选结果实际绘制，保存截图及进程树资源采样。

性能比较使用相同源文件、release 二进制和独立的新应用缓存。操作系统文件缓存、其他主机负载和 CPU 频率未控制；这些单次样本不能作为 P95 或稳定提速承诺。

## 2026-11-22 本机测量

输入为 `.bench/regular-1g.csv`：1,073,741,973 字节、6,509,896 行、12 列。比较对象是上一轮已支持渐进浏览、但筛选要等完整导入的版本，并非最早的原始版本。

| 指标 | 上一轮渐进浏览版 | 本轮最终版 |
| --- | ---: | ---: |
| 原生完整导入 | 15.214 秒 | 12.629 秒 |
| CLI 累计进程 CPU 时间 | 15.531 秒 | 17.078 秒 |
| 第 201 行开始的 256 行可读取 | 打开后 0.086 秒 | 打开后 0.076 秒 |
| 导入中提交条件后，首批 256 条匹配可读取 | 等完整导入后再查询 | 0.027 秒 |

这组完整导入墙钟时间减少 16.99%。第一轮配对样本为 14.552 → 12.664 秒，约减少 13%。流水线的收益来自阶段重叠，不能将墙钟耗时下降解释成 CPU 工作量同比降低；最终配对样本中的累计 CPU 时间有所增加。

最终版原生增量筛选在打开后约 0.072 秒提交条件，首批匹配可读时已有 32,968 条源记录、扫描了 32,768 条，发布了 328 条匹配并核对其中 256 条完整值。后台补齐到 65,099 条匹配，整个过程中查询 ID 相同，未在 EOF 后重扫前缀。结果索引为 520,792 字节，即 65,099 × 8 字节。

相同输入的全量排序结果缓存从上一轮桌面记录的 1,385,746,468 字节，变为本轮的 52,079,168 字节，减少 96.24%；后者正好为 6,509,896 × 8 字节。基础数据缓存均为 122,443,405 字节。这里比较的是结果缓存结构的大小，旧记录来自 2026-11-20，不将两日的排序时间和资源采样当成受控性能对照。
